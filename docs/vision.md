# llmems — Видение (North-star)

Статус: черновик v1.3 для валидации · 2026-05-21 · ветка experiment/graph-memory

Это стержень, по которому валидируются все решения. Сначала мысль, потом материя — архитектура и код вторичны и причёсываются под эти цели.

---

## 1. Зачем (главная цель)

Память для LLM, которая:

- не забывает важное,
- работает с человеком бесконечно долго,
- держит фокус на актуальном, не размывая внимание мусором.

Если в текущей теме всплывает что-то из прошлого опыта — этот опыт подсасывается в контекст сам на следующем шаге обработки, без явного вызова «вспомни» (без MCP-функции recall). Это другая концепция, чем чат, где события просто накидываются друг на друга.

**Пример применения:** долговременный собеседник, который всё помнит о тебе и легко возвращается к темам из прошлого.

---

## 2. Проблемы (мотивация)

**P1 — Замусоривание контекста / размывание фокуса.** В чат-режиме весь контекст без разбора льётся в «голову» модели. Накапливается разноплановый мусор, внимание размывается, модель путается и теряет фокус на актуальном.

**P2 — Конечное окно против бесконечной истории.** Окно контекста конечно, история бесконечна — значит, неизбежно нужно что-то «забывать» / сжимать. Сделать это, не потеряв важное и не сломав дешёвый кэш, нетривиально. (Сейчас в коде компактизируется весь диалог целиком — наивно: логичнее ужимать только старую «холодную» верхнюю половину.) Пометка: гипотетически полезное наблюдение.

**P3 — Единица памяти (гранулярность).** Чтобы релевантный прошлый опыт можно было точечно достать и вставить в контекст, память должна быть нарезана на правильные единицы. Слишком мелко — фрагмент теряет смысл в отрыве (висячие ссылки: «он» — это кто? когда? почему?), бесполезен или вводит в заблуждение. Слишком крупно — извлекается куча лишнего, и фокус снова замусоривается. Наивная нарезка ломает авто-инъекцию: достаём либо бессмысленное, либо неотбираемое.

**P4 — Память без структуры (плоский мешок).** Мемы лежат плоско, без связей и уровней. Тогда релевантный опыт нельзя достать «вместе с окрестностью», а граф вырождается в обычный — а для запроса с одним семантическим смыслом обычный граф бесполезен (см. эмпирику в §6). Нужна структура: время (мем = момент / событие / период), семантическая иерархия (часть-целое) и другие оси — чтобы при генерации собирать более полный контекст.

## 3. Целевая модель: память как фабрика контекста

Очень простой API из двух функций. Ключевая идея — **чистое разделение мутации и чтения**: `remember` меняет состояние, `getCurrentContext` его проецирует.

- **`remember(sessionId, fragment)`** — «запомнить». У этого метода **две роли**, а не одна:
  - **(а) Сохранить фрагмент** — положить входящий фрагмент (текст, возможно содержимое файла) в сырьё для последующего фонового переваривания. Фоновый индексатор накапливает сырьё и, когда набирается достаточно, переваривает его в атомарные мемы и заменяет сырьё мемами — как человек поспал: ощущение от вчера осталось, конкретика стёрлась.
  - **(б) Сдвинуть фокус** — обновить внутренний «вектор темы/фокуса» сессии с учётом этого фрагмента («сейчас хотим говорить про это»). И как следствие сдвига — **автоматически сходить в долговременное хранилище и подгрузить в рабочий кэш сессии новые релевантные мемы**, ставшие актуальными после смещения фокуса. Уже загруженные (закэшированные) мемы не трогаются; в кэш дописываются только по-настоящему новые релевантные мемы.

  То есть запрос в базу по релевантности (механизм «дрейфующий вектор → подгрузка новых мемов» из §4) теперь происходит **внутри `remember`**, а не внутри `getCurrentContext`. `remember` возвращает ack/void — переваривание идёт в фоне.

- **`getCurrentContext(sessionId)`** — «выдать текущий контекст». Это **чистая stateful-проекция**: метод **не принимает** никакого topic/query-аргумента. Он просто читает текущее рабочее состояние сессии (уже загруженные упорядоченные мемы в кэше + последние ещё не проиндексированные фрагменты) и сериализует его в единый текстовый блок, готовый к подаче в LLM. Поскольку все релевантные мемы уже подгружены предшествующими вызовами `remember`, `getCurrentContext` практически **не делает обращений к базе** — он дёшев, детерминирован и дружелюбен к кэшу.

  **Почему имя `getCurrentContext`, а не `prepareContext`.** Метод больше ничего не «подготавливает» — вся работа (сохранить, сдвинуть фокус, подгрузить релевантные мемы) уже сделана в `remember`. Здесь же только склейка готового и выдача наружу. Нюанс терминологии: слово «контекст» обычно означает то, что **предшествует** промпту, а здесь оно включает и текущую реплику (сырой хвост) — то есть это весь блок, идущий в LLM, вместе с последним высказыванием.

Итого чистый сплит: **`remember` = мутация состояния** (сохранить + сдвинуть фокус + подгрузить релевантные мемы); **`getCurrentContext` = чтение состояния** (сериализация в текст).

Суть: **память — это фабрика контекста для языковой задачи.** Авто-инъекция: релевантный прошлый опыт появляется в контексте сам на следующем шаге, без явного вызова recall.

### Поток одного хода

Последняя реплика пользователя **тоже** проходит через `remember`. Неважно, утверждает пользователь факт или задаёт вопрос — эта реплика сначала приходит в `remember` (он сдвигает фокус и подтягивает релевантные мемы), и только затем вызывается `getCurrentContext`, чтобы отрендерить контекст, который скармливается нижестоящей LLM для ответа/предсказания.

**`remember` вызывается на ОБА хода — и на реплику пользователя, и на ответ модели, СРАЗУ.** Ответ модели тоже сдвигает вектор фокуса и тоже полезен как материал для будущего опыта. Почему сразу, а не «потом, когда понадобится»: иначе теряем случай «робот сказал X, человек ушёл делать и не ответил» — информация о том, на чём остановились, просто пропадёт. Получается слоёнка: фраза → её мемы → фраза → её мемы.

```
реплика пользователя X
  → remember(sessionId, X)         [сохранить X, сдвинуть фокус, подгрузить релевантные мемы]
  → getCurrentContext(sessionId)   [сериализовать текущий кэш → текст]
  → подать в LLM
  → LLM отвечает Y
  → remember(sessionId, Y)         [сразу: сохранить ответ модели, сдвинуть фокус]
```

Отдельного понятия «query» нет — **запросом является сам последний запомненный фрагмент (фрагменты)**. Дрейфующий вектор темы/фокуса — это бегущая сводка последних `remember`.

### Мультисессионность и session id

Модуль памяти **мультисессионный**: несколько параллельных разговоров могут одновременно обращаться к **одному** модулю памяти. Поэтому рабочее состояние — вектор фокуса, кэш загруженных мемов и счётчик внеочередных дописываний (используемый для мягкой перестройки, см. §5) — **пер-сессионное**, ключуется по session id. А долговременное хранилище переваренных атомарных мемов (в pgvector) — **общее для всех сессий**.

Поэтому обе функции принимают session id:

- `remember(sessionId, fragment)` → возвращает ack/void (переваривание — в фоне);
- `getCurrentContext(sessionId)` → возвращает собранную строку контекста.

Концептуально: **общая долговременная память + пер-сессионное эфемерное рабочее состояние.** Где именно живёт пер-сессионное состояние (in-process-карта против персистентного хранилища) — деталь, которую уточним позже (см. §9).

## 4. Динамическая сборка контекста (stateful, бережно к кэшу)

**Дрейфующий вектор темы.** Каждый запомненный фрагмент чуть смещает вектор «о чём говорим». Запрос в базу по этому вектору («какие релевантные мемы ещё не подгружены») делает именно **`remember`** в момент сдвига фокуса — это часть мутации состояния (см. §3). `getCurrentContext` сюда не ходит: он лишь сериализует уже собранный кэш.

**Уже подгруженные мемы не трогаем.** Они остаются в закэшированной части (в начале промпта), «тихо плетутся», закэшированы, дёшевы. `remember` дописывает в кэш только по-настоящему новые релевантные мемы, не дублируя уже загруженные.

**Новые мемы дописываем после кэша** — перед живой перепиской, каждый с таймстемпом в XML-формате (`<mem ts="ISO8601">...</mem>`), чтобы нехронологический порядок не путал модель.

**Маркер автозагрузки (recalled-memory marker).** Блок динамически загруженных мемов (слои 2–3) открывается коротким маркером на естественном языке — «Loaded from memory:» по умолчанию. Маркер конфигурируем: если язык разговора известен, нужно передать перевод. Цель — модель явно различает автоматически подгруженный прошлый опыт и живую переписку, не трактуя его как только что сказанное.

**Дедупликация мем/сырьё при загрузке.** Перед добавлением нового мема в сессионный кэш проверяются два условия; мем исключается если выполняется хотя бы одно:

- **(а) Уже загружен** — мем уже присутствует в кэше сессии (O(1)-проверка по множеству id). Повторная загрузка того же мема расточительна и запутывает порядок слоёв.
- **(б) Его исходный фрагмент ещё активен (raw-present)** — чанк, из которого вырос мем, ещё не скомпактизирован: он присутствует в сырьевом хранилище со статусом `active`. В этом случае сырьё уже есть в сырьевом хвосте (слой 4) — мем взял бы на себя его роль преждевременно. Мем становится eligible для загрузки только после компактизации: когда исходный чанк переходит в `archived`, мем «принимает смену» у сырьёвого фрагмента.

**Два времени.** `ts` — это момент в **разговоре**, когда знание прозвучало (кто-то это сказал). Содержание мема при этом может относиться к **другой** дате — прошедшему или грядущему событию («в прошлом году переехал», «в следующую пятницу дедлайн»). Это **время события** вторично: оно живёт в деталях/типе мема (см. §6, тип «событие»), а **не** в `ts`. Не путать: `ts` отвечает на «когда это сказали», время события — на «когда это произошло/произойдёт».

**Слои контекста (явный порядок сборки):**

1. **Кэшированные мемы** (стабильный префикс) — то, что уже лежит в кэше сессии.
2. **Мемы, подгруженные сменой вектора** — новые релевантные мемы, дописанные после смещения фокуса (с таймстемпами).
3. **Мемы, связанные с сырым непроиндексированным фрагментом** — то, что подтянулось под ещё не переваренный хвост.
4. **Сам сырой хвост / текущая реплика** — в самом конце.

Хвост всегда пересчитывается: именно по нему подгружались мемы слоёв 2–3, и эти новые мемы уже сдвинули точку кэша — поэтому фиксировать хвост в кэше нельзя, он каждый ход собирается заново.

**Технический нюанс prompt-cache.** KV-cache кэширует именно префикс до точки разрыва. Поэтому стабильное держим в начале, новое дописываем в хвост — платим только за хвост.

**Recency-эффект работает в плюс.** Свежеподгруженные мемы попадают в конец, в зону максимального внимания модели — и они там уместны, потому что подгружены именно как релевантные текущей теме. Таймстемпы нужны, чтобы модель не путала «только что загрузили» с «только что произошло».

**Открытый вариант — интерливинг (попробовать, не решение).** Вместо группировки по слоям выше можно попробовать **чередование** «фраза → её мемы → фраза → её мемы» (солянка), при котором система помнит, **в какой момент что вспомнила**. Это `попробовать`, а не принятое решение: интерливинг **конфликтует** с группировкой выше (стабильный кэш-префикс vs перемешанный порядок ломает дешёвый кэш). Развести два подхода в эксперименте — какой даёт более полезный контекст.

## 5. Мягкая перестройка («компактизация через забывание»)

Когда разнобойных подгруженных мемов накопилось много (порог ~30, уточняется эмпирично), делаем одну операцию перестройки кэша:

- стираем устаревшие и нерелевантные мемы (те, что при перестройке набрали низкое косинусное сходство с текущим вектором фокуса);
- выживших упорядочиваем по времени — хронология восстанавливается;
- хвост перекэшируется заново (сдвигаем точку кэша).

Мемы, выброшенные при перестройке, **выходят из кэша вместе с dedup-записью**: они снова становятся eligible для загрузки при следующих запросах. Специального кода для этого не нужно — dedup-фильтр в `remember` опирается на актуальное множество id загруженных мемов, которое перестройка перестраивает заново.

Это аналог компактизации, но гораздо мягче: вместо пересказа — **забывание нерелевантного**. Делается редко (реже обычной компактизации), чтобы всегда оставалась свободная половина окна контекста как «комната».

**Экономическая логика.** Если держать дешёвые мемы в кэше дешевле, чем переиндексация — оставляем их (даже мусорные), чтобы не ломать кэш. Когда мусора накопилось много — выкашиваем.

## 6. Структура памяти как цель (фаза 2)

Это целевое состояние (Point B). Очерёдность зафиксирована в бидах: **baseline сначала** (минимальная фабрика контекста, замер), структура — **фаза 2, после замера baseline**. Концепты ниже — куда идём, а не что строим первым.

- **Типизация мемов.** У мема есть тип: «событие» (со своими деталями, в т.ч. время события), возможно «период». _(В коде уже есть незаполненное поле `fragmentType`: `fact | event | belief | plan | problem | insight` — туда это и ложится.)_
- **Иерархия уровней.** Год / квартал / месяц / день — разные уровни мема, строят иерархию. Верхние уровни **крупноблочны**: мем «год» не содержит «сходил в магазин», а события масштаба кварталов/месяцев; те, в свою очередь, более мелкие, расшифровывающие суть. Уровни появляются **органически** — только когда об уровне явно зашла речь (всплыло «ощущение от года» → система доспрашивает → детали сами укладываются в дерево). Высокий уровень = естественный пересказ вложенного, не искусственная агрегация. Дерево — частный случай графа.
- **Граф как досборка контекста (НЕ recall).** Найден узел → подтянуть его **окрестность** по каждой из 7 осей (`chronos`, `topos`, `agents`, `theme`, `cause`, `emotion`, `certainty`) → 10 найденных мемов превращаются в ~100, которые хорошо описывают объём знаний (крупные процессы + нюансы текущего фокуса). Цель — более полный контекст **при генерации**, а не точность поиска.
- **⚠ Эмпирическая осторожность.** Оси/проекции **для поиска** (recall) уже проигрывали наивному вектору: recall@5 0.524 (baseline) → 0.369 (per-axis), в графовом прогоне ещё хуже. Но применение «оси для досборки» ≠ «оси для recall» — поэтому провал recall эту идею **не хоронит**. Однако строим её только после baseline и измеряем прирост **отдельно**.

## 7. Принципы / ценности

### Принципы решения (как отвечаем на проблемы)

1. **Релевантность вместо накопления → P1.** В контекст попадает только релевантное текущему фокусу, и попадает само (авто-инъекция, без явного вызова recall). Дрейфующий вектор фокуса — единственный источник правды о том, «что сейчас важно».
2. **Забывание вместо пересказа → P2.** Сжимаем, выкашивая нерелевантное, а не пересказывая всё (мягкая перестройка, экономный reaping). Трогаем только холодную верхнюю половину; всегда держим свободную «комнату» в окне.
3. **Бережность к кэшу: дополнять, не переставлять → P2 (стоимость).** Стабильное — в начале (закэшированный префикс), новое — в хвост; перестройка редкая и намеренная, платим только за хвост.
4. **Атомарность мема → P3.** Каждый мем — самодостаточный сегмент об одном предмете, понятный в отрыве от остальных; правильная гранулярность → одновременно отбираем и осмыслен. _(Уже зашито в промпте выделения мемов: «a mem is a SEGMENT of conversation about one subject». Если промптинг или настройки отойдут от этого принципа — об этом нужно явно сказать пользователю.)_
5. **Явное время (`ts`), а не позиция.** Источник времени для модели — атрибут `ts`, а не позиция фрагмента в контексте (мемы дописываются не в хронологическом порядке) — корректность авто-инъекции.
6. **`remember` мутирует, `getCurrentContext` проецирует.** Чёткое разделение записи и чтения; единственный источник правды о текущем фокусе один.
7. **`remember` на оба хода.** В память идут и реплики пользователя, и ответы модели, сразу — иначе теряем «на чём остановились», если человек ушёл и не ответил.
8. **Структура — ради полного контекста при генерации, не ради recall.** Типизация, иерархия и графовая досборка нужны, чтобы при генерации собрать более полный контекст, а не чтобы точнее искать (recall наивным вектором уже сильнее — см. §6).

### Ценности проекта (мета)

- **Сначала мысль, потом материя** — видение и цели первичны, архитектура и код вторичны и причёсываются под цели.
- **Quality > Speed** — один ясный путь без костылей и fallback.

## 9. Открытые вопросы (решим в roadmap/architecture)

- **Всегда ли `remember` двигает фокус?** Или массовые / ingest-style вызовы `remember` (предзагрузка, импорт файла) должны уметь сохранять без сдвига фокуса — store-without-shifting?
- **Где персистить пер-сессионное рабочее состояние** (in-memory-карта против durable-хранилища) и как сессия создаётся / истекает (lifecycle, TTL, очистка).
- **Enum типов мема** — взять существующий `fragmentType` (`fact | event | belief | plan | problem | insight`) или расширить осью `period`? (см. §6).
- **Размер окрестности досборки против P1** — насколько широко тянуть окрестность узла, чтобы ~100 мемов не замусорили фокус; как удержать крупноблочность верхних уровней (баланс «полный контекст» vs «размывание»).
- **Интерливинг против группировки** — слоёнка «фраза → её мемы» (с памятью о моменте вспоминания) против группировки по слоям §4; конфликтуют по кэшу, развести в эксперименте.
- **Порог перестройки** (~30 разнобойных мемов) — подобрать эмпирично.
- **Надёжность временны́х рассуждений** — корректно ли LLM рассуждает о времени по 30+ разнобойным `ts`-мемам; нужен эмпирический тест (риск на тонких временны́х цепочках).
- **Формат мемов в контексте:** XML с `ts` (предпочтительно) против JSONL.
- **Где место графа:** структура и графовая досборка — **фаза 2**, gated на baseline (строим и измеряем только после замера минимальной фабрики контекста; см. §6).

## 10. Модель эмбеддингов (фаза 1)

**Модель:** `openai/text-embedding-3-small`, 1536 dim, через OpenRouter. Один вектор на текст — никакого мультиразрешения.

Ранний вариант дизайна предполагал многоразрешённые эмбеддинги по схеме Matryoshka (1024 / 256 / 64 dim): идея в том, что меньшие срезы дают быстрый грубый отбор, а полный вектор — точный. На практике мультиразрешение не дало измеримого прироста качества на задаче подбора релевантных мемов и было упразднено. В кодовой базе осталась историческая метка: поле `EmbeddingValue.compact` хранит основной (и единственный) 1536-dim вектор. Переименование в `EmbeddingValue.vector` запланировано в отдельном бидe (llmems-fqx) и не блокирует фазу 1.
