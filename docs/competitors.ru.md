# Конкуренты и аналоги — память агентов на LLM

> Перевод с английского оригинала [competitors.md](competitors.md). При расхождениях источником истины считается английская версия.

> Последнее обновление: 2026-06-08. Источник: `materials/research-2026-06-08-llmems-alternatives.md` (4 итерации исследования).

## Зачем этот документ

Цель llmems — лёгкая встроенная самостоятельно размещаемая TypeScript-библиотека для построения контекста с фоновой дебаунс-суммаризацией и без облачного бэкенда. Этот документ отслеживает, кто ещё решает ту же задачу, что можно у них перенять, и по каким бенчмаркам следует измерять результаты. Подход прагматичный: если один из конкурентов подходит — принять его; если нет — строить своё, но с открытыми глазами.

## Что считается конкурентом: конструктор контекста vs хранилище памяти

Ключевая ось классификации — **как вызывающий код взаимодействует с системой памяти**:

- **Конструктор контекста (тип A — полная обёртка):** оборачивает сам вызов LLM. Вызывающий отправляет сообщение и получает ответ ассистента; внедрение памяти происходит прозрачно внутри вызова. `OpenRouterChat` из llmems относится к этому типу.
- **Конструктор контекста (тип B — поставщик блока контекста):** не вызывает LLM; вместо этого возвращает готовую строку-блок для промпта, которую вызывающий вставляет в свой системный промпт перед обращением к LLM.
- **Хранилище памяти:** вызывающий вызывает `search()` и самостоятельно собирает итоговый промпт. Это не конструктор.

llmems = **тип A**. Именно эта призма определяет, кто является прямым конкурентом.

## Четыре финалиста: детальный анализ «строить vs принять»

Эти четыре системы — наиболее близкие конструкторы контекста к llmems; по ним проводилась оценка по критерию «принять vs продолжать разработку».

### Memori (MemoriLabs)

**Зрелость:** ~15 200 звёзд на GitHub; Python + TypeScript + Rust; v3.3.6 (май 2026, компания: MemoriLabs / GibsonAI). TypeScript SDK молодой (запущен в марте 2026). SaaS-уровень готов к продакшену; ветка BYODB новее и менее обкатана.

**Механизм памяти и контекста:** Семантические тройки (субъект–предикат–объект). Режим BYODB: fastembed / all-MiniLM локально, собственный Postgres. `llm.register(client)` оборачивает LLM-клиент вызывающего и прозрачно внедряет факты. Извлечение на каждое сообщение — без дебаунса (issue [#366](https://github.com/MemoriLabs/Memori/issues/366), без ответа мейнтейнеров на дату исследования).

**Самохостинг и привязка к вендору:** Apache 2.0 SDK + собственный Postgres для хранения. Однако функция **Advanced Augmentation** (шаг извлечения и внедрения) маршрутизируется через их облако: бесплатный уровень ограничен по IP; для продакшена требуется `MEMORI_API_KEY`. Ключевая ценность имеет реальную привязку к вендору.

**Ограничения / незрелые места:**
- Извлечение на каждое сообщение дорого по токенам при масштабировании (issue #366, без реакции мейнтейнеров).
- Аугментация за облачными ограничениями скорости — противоречит принципу «нулевых внешних вызовов».
- Режим BYODB незрел; в некоторых уровнях требуется указание авторства.

**Что перенять:** Эргономика интеграции без рефакторинга через `llm.register(client)` — паттерн, достойный копирования. Семантические тройки как структурированный формат памяти. Локальный fastembed для эмбеддингов без отдельного сервиса.

**Вердикт как замена llmems:** Не подходит. Ключевая функция (аугментация) требует их облака. Противоречит инварианту «нулевых внешних вызовов кроме выбранного LLM-эндпоинта».

### SuperMemory

**Зрелость:** ~26 100 звёзд (наибольшее из всех обследованных); TypeScript 64.6%; MIT на открытых репозиториях. Заявляет лидерство на LongMemEval и LoCoMo (см. инвариант честности в разделе о бенчмарках); задержка извлечения менее 300 мс.

**Механизм памяти и контекста:** Извлекает статические долгосрочные факты + динамические свежие факты на каждый разговор. Разрешение противоречий («переехал в SF» вытесняет «живу в NYC»). Автоматическое забывание фактов, ограниченных по времени («экзамен завтра»). Гибридный семантический + ключевой поиск. Infinite Chat / Memory Router работает как прокси `baseURL` — обёртка типа A.

**Самохостинг и привязка к вендору:** Это критическое ограничение. Ядро извлечения и извлечения памяти — **закрытый исходный код**. Открытые репозитории содержат только фронтенд, MCP-коннекторы и SDK-обёртки. Официальный самохостинг — корпоративный уровень на Cloudflare Workers. Прокси маршрутизирует промпты через их серверы. Существует неофициальный форк сообщества (`s11ngh/supermemory-selfhosted`), но это не официальный продукт.

**Ограничения / незрелые места:**
- Основная логика проприетарная — нельзя самостоятельно разместить ценную часть.
- Все данные промптов проходят через их инфраструктуру.
- Для корпоративного самохостинга — только развёртывание на Cloudflare.

**Что перенять:** Разрешение противоречий + автоматическое забывание фактов с временным ограничением — это сильнейшая идея в данном пространстве, отсутствующая в llmems. Паттерн прокси Memory Router как альтернативная поверхность интеграции. Их [MemoryBench](https://github.com/supermemoryai/memorybench) — рекомендованный инструмент для бенчмаркинга (см. раздел о бенчмарках).

**Вердикт как замена llmems:** Не подходит. Только идеи, не код.

### Mastra

**Зрелость:** ~24 900 звёзд; TypeScript 99.3%; `@mastra/core` v1.41.0 (ядро 1.x — стабильная ветка); ежедневные релизы; основана командой бывшего Gatsby, YC W25. Двойная лицензия: Apache 2.0 ядро + проприетарная корпоративная редакция (директория `/ee/`).

**Механизм памяти и контекста:** Четырёхуровневая система: история разговора + рабочая память + семантический поиск (RAG) + наблюдательная память (фоновое авто-сжатие, введено в феврале 2026). Подключаемое хранилище: PostgreSQL/pgvector (IVFFlat или HNSW), LibSQL, MongoDB. `agent.generate(msg, { memory: { threadId, resourceId } })` — конструктор типа A. Также предоставляет процессор `TokenLimiter` и интерфейс `MemoryProcessor` для фильтрации того, что попадает в контекст. Важно: это полноценный **фреймворк агентов**, не тонкая обёртка.

**Самохостинг и привязка к вендору:** Полностью самохостируемый с собственным Postgres; Apache 2.0 ядро не требует облака. Привязка мягкая: корпоративные функции в `/ee/`; принятие Mastra означает переход на их модель агентов.

**Ограничения / незрелые места:**
- **Краш issue [#5214](https://github.com/mastra-ai/mastra/issues/5214):** нарушение первичного ключа при двойной вставке во время семантического поиска + комбинации с Vercel AI SDK — не разрешено на дату исследования.
- Полезные нагрузки вызовов инструментов могут переполнить контекстное окно, если не отфильтровать перед внедрением.
- Тяжёлый фреймворк (не тонкий слой); 187+ открытых issues; периодические ломающие изменения в минорных релизах.
- Нет суммаризатора на основе дебаунса; триггер наблюдательной памяти отличается от дебаунса llmems.

**Что перенять:** Подключаемый pgvector с явным выбором HNSW vs IVFFlat + конвейер `MemoryProcessor` / `TokenLimiter`. Наблюдательное сжатие старых сообщений в плотные резюме. TypeScript-ориентированный DX для потоков и ресурсов. Инструменты для оценок и наблюдаемости.

**Вердикт как замена llmems:** Подходит с оговорками — единственный полностью самохостируемый + TypeScript + Apache + конструктор в обзоре. Но это фреймворк, не тонкий слой; подсистема памяти ещё зреет; принятие означает жизнь внутри Mastra.

### Letta (бывший MemGPT)

**Зрелость:** ~23 200 звёзд; Python 99.5% ядро; v0.16.8 (0.x — API не заморожен); 177 релизов; с венчурным финансированием (letta-ai). TypeScript — только клиентский SDK; ядро — Python-сервер.

**Механизм памяти и контекста:** Иерархия в стиле ОС: основная память (всегда в окне, редактируемые «блоки») → память воспоминаний (последние ходы, векторный поиск) → архивная память (неограниченная долгосрочная, вектор). LLM сам управляет перемещением памяти через вызовы функций (`memory_append`, `memory_replace` и др.). `client.agents.messages.create()` — тип A. Без дебаунса.

**Самохостинг и привязка к вендору:** Apache 2.0, но запуск означает развёртывание **полноценного Python-сервера**: Docker, ~42 таблицы в БД при старте, обязательный Postgres по `LETTA_PG_URI`. TypeScript-потребители обращаются к нему через HTTP-клиентский SDK. Не встроен в процесс.

**Ограничения / незрелые места:**
- Накладные расходы рантайма: >1.5 ГБ памяти под нагрузкой; сообщения о OOM-убийствах; ~50–200 МБ/месяц роста БД на агента.
- Требует явной настройки эмбеддингов; таймауты 504 на длинных вызовах.
- 0.x означает нестабильность API; для TypeScript-проекта это сторонний Python-сервер рядом с вашим процессом.

**Что перенять:** Многоуровневая архитектура памяти с явной видимостью в окне (проверяемые, редактируемые блоки основной памяти). LLM-управляемое самоуправление памятью как будущий режим. Концепция прямо проверяемых и редактируемых блоков памяти для отладки.

**Вердикт как замена llmems:** Не подходит. Python-сервер, не встроенный TypeScript.

## Вердикт: строить vs принять

Ни один финалист не удовлетворяет полностью требованию «лёгкая встроенная самохостируемая TypeScript-обёртка, нулевой облачный бэкенд, без зависимости от агентного фреймворка». Ниша реальная и незаполненная:

- **Mastra** — наиболее близкий вариант (самохостинг + TS + Apache + конструктор), но это тяжёлый агентный фреймворк с ещё зреющей подсистемой памяти. Принятие означает перенос всего кода агентов на модель Mastra.
- **SuperMemory** лидирует по бенчмаркам, но его ядро — закрытый SaaS.
- **Memori** имеет правильный паттерн DX, но ключевая функция (аугментация) требует их облака.
- **Letta** обладает наиболее сложной моделью памяти, но является Python-сервером.

Продолжение разработки llmems обосновано. Дифференциаторы, которые нужно защищать:

1. **Всё в процессе** — нулевые внешние вызовы, кроме выбранного LLM-эндпоинта.
2. **Токен-экономный дебаунс** — фоновая суммаризация, запускаемая по времени простоя, а не при каждом сообщении.
3. **Тонкая обёртка, не фреймворк** — вызывающий сохраняет существующий код; `OpenRouterChat` является drop-in-заменой.

## Уроки реализации — что перенять и КАК

Приоритетные идеи для внедрения с конкретной привязкой к llmems:

**Разрешение противоречий + автоматическое забывание фактов с временным ограничением (SuperMemory)**
SuperMemory обнаруживает, когда новый факт вытесняет старый («переехал в SF» → помечает «живу в NYC» как вытесненное), и автоматически удаляет факты с временными ограничениями («экзамен завтра» → истекает через 24ч). В llmems сегодня нет обнаружения конфликтов. Как применить: при `insert_mem` выполнять семантический поиск близких существующих записей, затем использовать небольшой LLM-вызов для классификации как ADD / UPDATE / NOOP / DELETE (тот же алгоритм, что использует Mem0, задокументирован в их статье arxiv.org/abs/2504.19413). Добавить столбец `expires_at` в таблицу `mem` для явных фактов с временным ограничением; суммаризатор дебаунса должен обнаруживать маркеры истечения срока в тексте.

**Прозрачная обёртка `llm.register(client)` (Memori)**
Ключевой UX-инсайт Memori: вызывающий не рефакторит существующий код. Он вызывает `llm.register(myOpenAIClient)` один раз, и каждый последующий вызов `client.chat.completions.create()` автоматически внедряет память. Как применить в llmems: `OpenRouterChat` уже является обёрткой, но предоставление фабричной функции `register(existingClient)`, возвращающей обогащённый памятью прокси существующего `openai`-совместимого клиента, позволит принять без рефакторинга.

**Подключаемый pgvector индекс: HNSW vs IVFFlat + `MemoryProcessor` / `TokenLimiter` (Mastra)**
Mastra предоставляет тип индекса как опцию конфигурации и применяет шаги `MemoryProcessor` (включая `TokenLimiter`) для фильтрации и усечения извлечённых воспоминаний перед внедрением. Как применить: llmems должен предоставлять `indexType: 'hnsw' | 'ivfflat'` в конфигурации хранилища (HNSW лучше для больших коллекций; IVFFlat быстрее строится, но деградирует при масштабировании). Реализовать цепочку `MemoryProcessor`: как минимум, фильтр по бюджету токенов, усекающий внедряемый контекст до настраиваемого потолка токенов перед попаданием в промпт.

**Наблюдательное сжатие старых сообщений в плотные резюме (Mastra)**
Наблюдательная память Mastra сжимает более старые ходы разговора в плотные резюме в фоновом режиме. Это отличается от дебаунса llmems: Mastra запускается по счётчику ходов или давности, llmems — по времени простоя. Как применить: рассмотреть дополнительный триггер — после N ходов (настраиваемо, напр. 20) принудительно запускать проход суммаризации вне зависимости от времени простоя. Это покрывает высокочастотные разговоры, где время простоя никогда не срабатывает.

**Многоуровневые / проверяемые блоки памяти (Letta)**
Letta делает основную память (содержимое, всегда находящееся в окне) непосредственно читаемой и редактируемой через API. Разработчики могут точно проверить, что находится в контекстном окне, и редактировать блоки памяти для отладки или исправления. Как применить: предоставить запрос `mem.list({ inWindow: true })`, возвращающий, какие записи в данный момент внедрены в контекст, и `mem.update(id, content)` для ручного исправления. Это превращает llmems из чёрного ящика в проверяемую систему.

**Идемпотентная вставка / дедупликация (урок из краша Mastra #5214)**
Краш Mastra #5214 — нарушение первичного ключа при двойной вставке во время параллельного семантического поиска + вставки. Как применить: `insert_mem` в llmems должен быть идемпотентным — использовать `INSERT ... ON CONFLICT DO NOTHING` по хэшу содержимого, и удерживать консультативную блокировку сессии во время сброса дебаунса для предотвращения параллельных вставок одного результата суммаризации.

**Фильтрация полезных нагрузок вызовов инструментов перед внедрением (Mastra)**
Результаты вызовов инструментов (особенно большие JSON-нагрузки от вызовов функций) могут переполнить контекстное окно при наивном внедрении в память. `MemoryProcessor` Mastra фильтрует их. Как применить: в суммаризаторе дебаунса пропускать или усекать сообщения, где `role === 'tool'` и `content.length > threshold`; вместо внедрения сырой нагрузки суммировать семантический результат инструмента.

## Ограничения конкурентов, которые нужно обойти

Пять главных режимов отказа, выявленных в обследованных системах, с прямыми последствиями для дизайна llmems:

1. **Расточительность токенов на каждое сообщение (Memori [#366](https://github.com/MemoriLabs/Memori/issues/366)):** извлечение фактов при каждом сообщении дорого. Дебаунс-подход llmems объективно более экономичен по токенам; это преимущество следует измерить (см. Бенчмарки — ConvoMem).
2. **Дедупликация / идемпотентность при вставке (Mastra [#5214](https://github.com/mastra-ai/mastra/issues/5214)):** параллельные вставки при поиске вызывают краши. Использовать дедупликацию по хэшу содержимого + консультативные блокировки.
3. **Переполнение полезной нагрузки вызовов инструментов (Mastra):** сырые результаты инструментов, внедрённые в контекст памяти, переполняют окно. Фильтровать нагрузки с `role='tool'` перед внедрением.
4. **Рост pgvector + деградация индекса (OOM Letta; IVFFlat vs HNSW в Mastra):** наивный IVFFlat деградирует по мере роста коллекции; Letta сообщает об OOM-убийствах и росте ~50–200 МБ/месяц на агента. Планировать HNSW с самого начала и реализовать периодическое удаление малорелевантных записей.
5. **Скрытый облачный бэкенд на ключевой функции (аугментация Memori, прокси SuperMemory):** оба позиционируются как «самохостируемые», но ценная функция маршрутизируется через их облако. Инвариант «нулевых внешних вызовов кроме LLM-эндпоинта» должен быть явным, проверяемым контрактом в llmems — а не побочным эффектом.

### Почему ConvoMem стратегически важен

Центральный тезис ConvoMem напрямую подтверждает нишу дизайна llmems:

- **До ~150 диалогов:** наивный полный контекст набирает 70–82% точности. Чистая RAG-память (в стиле Mem0) — только 30–45% — RAG вредит при коротком контексте.
- **После 150–300 диалогов:** RAG окупается — 95× экономия токенов при небольшом падении точности.
- **Блочное извлечение (≈ дебаунс-подход llmems):** сохраняет 70–75% точности при 30× ускорении через параллелизацию.

Это даёт объективную рамку для позиционирования: дебаунс llmems превосходит чистый RAG в режиме до 150 диалогов И более экономичен по токенам, чем полный контекст. ConvoMem позволяет точно это измерить.

Игла в стоге сена LongMemEval: точность падает на 30–60% по сравнению с оракульным извлечением на ~40–50 отвлекающих сессиях (~115К токенов, 500 вопросов). Задачи обновления знаний и воздержания от ответа напрямую зондируют места, где записи памяти llmems могут содержать устаревшие или конфликтующие факты.

### Минимальная обвязка для разработки

TypeScript-адаптер для llmems под интерфейс MemoryBench, в два этапа:

**Этап приёма данных (`ingest(sessions)`):** прогонять сессии через `OpenRouterChat`, чтобы дебаунс-суммаризация порождала записи.

> **Критически важно:** предоставить тестовый хук для принудительного синхронного сброса дебаунса перед фазой запросов — `await session.flushDebounce()` или эквивалент. Без этого записи ещё не записаны в момент запроса, и точность будет ложно занижена. Это та же проблема, что задокументировал Zep («приём занимает несколько минут после загрузки»); решить её явно в тестовой обвязке.

**Фаза запросов (`answer(question)` / `getContext(question)`):** использовать режим `dryRun` для возврата собранной строки контекста (для метрик извлечения: Recall@k, NDCG@k) и/или передачи в LLM для прямого ответа (для метрик точности на основе оценщика).

**Обёртка LLM-оценщика:** обернуть GPT-4o (или модель класса Flash — ConvoMem показал, что Flash эквивалентен GPT-4o для оценки при ~8× меньшей стоимости).

**Инкрементальная валидация:** первый прогон на 10–20 вопросах (~$0.005–0.05), убедиться, что конвейер работает корректно, затем масштабировать до 500+ вопросов.

### Инвариант честности — обязателен

Строго следовать протоколу LoCoMo:
- Использовать только категории 1–4 (фактическая/временная/многошаговая/состязательная).
- Запускать 10 итераций; сообщать среднее ± дисперсию.
- Использовать идентичные промпты для llmems и базовой линии.
- **Не** настраивать промпт оценщика в пользу llmems.

**Предостерегающий случай (Zep / LoCoMo):** Zep сообщил 84% на LoCoMo; корректное пересчитывание дало 58.44% ([zep-papers #5](https://github.com/getzep/zep-papers/issues/5)). Завышенное число получилось из-за: включения категории 5 (состязательной) в числитель при исключении из знаменателя; изменённых промптов; одного прогона вместо 10. Не повторять этого.
